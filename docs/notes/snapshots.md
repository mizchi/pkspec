# Snapshot kinds in pkspec

pkspec ships three orthogonal snapshot mechanisms. Each has a
different storage location, a different update workflow, and a
different set of trade-offs. Pick the one that matches what the
snapshot is really protecting.

## At a glance

| kind          | what it captures                              | where it lives                                          | how to update                  |
| ------------- | --------------------------------------------- | ------------------------------------------------------- | ------------------------------ |
| `byte`        | exact bytes of stdout / stderr                | `<workdir>/.pkspec/snapshots/<name>.bytes`           | `pkt run --refresh-snapshots` (and `pkt exec --refresh-snapshots` for the subprocess path) |
| `inline`      | exact bytes of test or step stdout / stderr   | inside the `Test.pkl` source itself (`inlineStdout = "..."`) | `pkt exec --update-inline-snapshots` |
| `ai-verdict`  | a fuzzy pass/fail judgement on a body         | `<workdir>/.pkspec/ai-snapshots/<name>.json`         | `pkt exec --refresh-ai`        |
| `http`        | the full response (status / headers / body) of one HTTP request | `<workdir>/.pkspec/http/<name>.json`                 | `pkt exec --refresh-http` (and `--http-replay-only` for CI) — see `docs/notes/cassettes.md` |

These never stack; a single test pins or polls or judges, but the
runner has no opinion on which it should be. Authors choose per-Test
and per-Step.

## `byte` (`ReferenceSnapshot`)

Per-test only. `expectStdoutSnapshot` / `expectStderrSnapshot` reference
a `ReferenceSnapshot` whose `name` resolves to a file under
`.pkspec/snapshots/`. Optional `generator` is itself a Test whose
stdout becomes the snapshot when the file is missing or refreshed.

Use when:

- the captured output is binary / large / structured, and you would
  rather review the file directly than read it inline,
- the snapshot is generated by a *reference* implementation (port
  testing) and you want the consumer's output to match it byte-exact.

Skip when:

- the output is small enough that an inline snapshot is more readable
  in code review,
- the assertion is structural (use `expectBodyJsonPath`) rather than
  byte-exact.

## `inline` (`inlineStdout` / `inlineStderr`)

Per-test (Test.cmd output) and per-step (Step.cmd stdout). Opt in by
setting the field to `""` (or any other string). The runner then
reports a mismatch on subsequent runs and, when invoked with
`pkt exec --update-inline-snapshots`, rewrites the Pkl source
in-place replacing the prior value with the captured bytes encoded
as a Pkl double-quoted string. The default value `null` means "no
inline assertion here" — the runner skips it entirely.

The Test or Step must have a `name` field — that is what the rewriter
uses to find the right object literal in the source. Anonymous steps
that try to use `inlineStdout` are reported as errored, not silently
matched against the wrong block.

Use when:

- the output is small (a line or two, a JSON blob you want to see
  alongside the test) and reviewers benefit from seeing it in the diff,
- you want a snapshot that survives `git mv` / module reorganisation
  without re-tracking a separate file path.

Skip when:

- the output is large (the encoded string would dominate the file),
- the output contains genuinely binary bytes (the encoder uses
  `\u{XX}` escapes for control chars, but byte streams full of
  arbitrary 0–31 values get unreadable fast).

### Caveats

- Multi-line values are encoded as a single line with `\n` escapes.
  This keeps the rewriter trivial; the readability cost is paid in
  exchange for not having to parse Pkl multi-line string syntax.
- The rewriter is regex-driven, not AST-driven. It finds the first
  `name = "<the-name>"` line in source and walks `{` / `}` to bound
  the enclosing object — robust enough for normal authoring, but not
  for hand-written modules that, say, embed a brace inside a string
  literal.
- Source rewrites are atomic (`<file>.pkspec.tmp` + rename).
  Concurrent step rewrites within the same run serialise on an
  `Executor`-level mutex.

## `ai-verdict` (`AiAssertion`)

Per-step. The judge command produces a pass/fail verdict + an
explanation; the runner caches both keyed by `sha256(prompt + body)`.
On a hit the judge is not invoked. On a miss the judge runs and the
snapshot is rewritten.

Use when:

- you need a fuzzy claim about the response ("the message reads as a
  user-facing apology in English") that no deterministic regex
  captures cleanly,
- you want CI cost to stay bounded (cache hits skip the cmd entirely).

Skip when:

- a deterministic check would do — `expectStatus`, `expectBodyEquals`,
  `expectBodyJsonPath` are cheaper, faster, and don't need a judge.

See `docs/notes/ai-assertion.md` for the full contract, refresh
semantics, and stale-cmd warning behaviour.

## Choosing between them

```
Is the assertion fuzzy (semantic, not byte-exact)?
└── yes → ai-verdict (`expectAi`)
└── no
    ├── Output is small + you want it in the diff?
    │   └── inline (`inlineStdout` / `inlineStderr`)
    └── Output is large / binary / generated by a reference impl?
        └── byte (`expectStdoutSnapshot`)
```

A fifth dimension — *what is intended to be checked but not yet
implemented* — is covered by `tags { "spec" }` + empty body; see
`docs/notes/spec.md`. The runner reports those as pending and `pkt
spec` renders them with an unchecked checkbox.

In all three cases the snapshot file (or rewritten source) is part of
the test contract — commit it. A reviewer reading a change to
`.pkspec/snapshots/` or a moved `inlineStdout = "..."` line is the
intended flow; it is what makes a snapshot trustworthy.
